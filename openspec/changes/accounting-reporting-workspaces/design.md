## Context

`/reports` and `/taxes` currently use generic record pages. EÜR, UStVA, EKS, and DATEV services exist but are not composed into the production route graph; GuV and ZM calculators are absent. Current EÜR code accepts a year but always initializes the 2025 internal line layout. Current DATEV code emits header format version 7, a nine-column body, and account fallbacks. The official DATEV contract describes a structured CSV with a versioned header and booking-field layout.

The proposed financial source is not accepted. `balanced-journal-postings-and-settlement-events` is still `REVISE`, and its required `invoice-money-invariants` prerequisite remains unresolved. This change MUST NOT describe that source as accepted, calculate report totals from invoice gross amounts or unconfirmed bank rows, or mark provisional totals complete.

## Goals / Non-Goals

**Goals:**

- Provide typed, localized workspaces with exact report period and source/version provenance.


### Report selection, service, and route contract

The router owns only canonical route/query parsing. It converts the documented report selection into a typed `ReportSelection`; the composed `ReportingWorkspaceUseCase` dispatches to the typed report use case and returns a `ReportWorkspaceResult` containing availability, exact period endpoints, versions, unresolved count, and source IDs. Pages render that result and never query tables or calculate values. Unsupported/missing query combinations render a typed invalid-selection or unavailable state while preserving the route and query.

| Route/deep link | Typed owner/use case | Period inputs | Result/availability boundary | Primary action |
|---|---|---|---|---|
| `/reports` or `/taxes` with no report query | `ReportCatalogUseCase.list` | None | Typed report choices and each choice's availability; no raw records | Select report |
| `/reports?report=euer&year=2025` | `EuerReportUseCase.preview` | Supported calendar year | `ReportWorkspaceResult<EuerPreview>`; only the versioned 2025 form and accepted source can return available | Preview |
| `/reports?report=eks` | `EksReportUseCase.availability` | None until an accepted Bewilligungszeitraum contract exists | Unavailable result names the missing form/period contract; no calendar-year surrogate | Show unavailable state |
| `/reports?report=guv&year=YYYY` | `GuvReportUseCase.preview` | One supported calendar year | Management preview only with accepted posting source, mapping, and period | Preview |
| `/reports?report=datev&month=YYYY-MM` | `DatevExportUseCase.create` | One calendar month per EXTF file | Validated local artifact only when pinned header/format and all source mappings pass | Create DATEV file |

The `/reports` and `/taxes` route selection and each owner's typed use case are part of the `typed-route-workspaces` capability delta. `ReportWorkspaceResult` has one availability state (`available`, `unavailable`, or `invalidSelection`) and, when available, carries the immutable typed report value. DATEV history uses the existing validated artifact lifecycle.
- Correct the maintained accounting contracts before wiring calculators to them.
- Make unsupported tax years, periods, transaction types, incomplete mappings, and unapproved accounting dependencies unavailable with a reason.
- Emit only the version-pinned DATEV file described here; preserve the maintained safe-path and artifact-history rules.

**Non-Goals:**

- Implement balanced posting, settlement, or invoice-cent allocation rules.
- Infer a fiscal calendar, tax filing cadence, business type, or Finanzamt notice from transaction totals.
- Produce EÜR, EKS, GuV, UStVA, or ZM files or submit reports to ELSTER/BZSt.
- Claim DATEV compatibility from a locally generated sample without the official format validator and a test import.

## Decisions

1. **Use an explicit availability gate.** A report result is available only when its maintained calculation contract, period, required data fields, and source contracts are present. Financial totals that depend on balanced postings or settlements remain unavailable until both `balanced-journal-postings-and-settlement-events` and `invoice-money-invariants` have independently approved contracts, including any required `CHANGES_APPLIED: yes`. An unavailable report exposes a localized reason and source-record links where available; it does not substitute journal totals, invoice amounts, or positive unconfirmed bank transactions.

2. **Use only declared period boundaries.** All date ranges are start-inclusive and end-exclusive in ISO dates. EÜR, management GuV, and `AccountingPeriodSummary` use a calendar year (`YYYY-01-01` through next `YYYY-01-01`); no non-calendar fiscal-year behavior is inferred. EÜR supports only the 2025 form version in this proposal. BMF published the 2025 form on 29 August 2025 and the separate 2026 form on 1 September 2026; a 2026 request SHALL be unavailable until its own field map and fixture are accepted. No year may silently reuse the 2025 form ([BMF Anlage EÜR 2025](https://www.bundesfinanzministerium.de/Content/DE/Downloads/BMF_Schreiben/Steuerarten/Einkommensteuer/2025-08-29-anlage-EUER-2025.html), [BMF Anlage EÜR 2026](https://www.bundesfinanzministerium.de/Content/DE/Downloads/BMF_Schreiben/Steuerarten/Einkommensteuer/2026-09-01-anlage-EUER-2026.html)). UStVA follows its configured monthly or quarterly calendar period. The supported ZM preview is a calendar month. DATEV creates one file per calendar month and uses a 1 January business-year start; other fiscal calendars remain unavailable until explicitly supported.

3. **Version the EÜR form independently from its calculation source.** The only form contract exposed here is Anlage EÜR 2025 for tax year 2025. The mapping fixture SHALL bind each internal EÜR line to the 2025 form label and official field identifier, data type, sign/amount rule, and required/blank behavior. An internal `euer_zeile` number is not itself proof of an official field mapping. A 2026 or later form remains unavailable until a reviewed contract and fixture exist. Even for 2025, calculation remains unavailable while the balanced-posting, settlement, or money-source prerequisite is unapproved.

4. **Keep the summary annual and source-identical.** `AccountingPeriodSummary` reports one supported calendar year and reuses the corresponding report result; it does not run parallel SQL. Income, expense, profit, margin, and tax figures carry their calculation/source version and unresolved-input count. The summary is complete only when the accepted accounting source and matching EÜR contract are available. Until then, dashboard widgets show an unavailable state and no estimated number as a complete total. Month and quarter summary modes are not offered.

5. **Limit this ZM contract to supported outgoing goods supplies.** A supported row is an outgoing business supply qualifying under §6a(1) UStG, made to a taxable-person recipient in another EU Member State with a valid customer USt-IdNr; the new-vehicle exception for a purchaser without a USt-IdNr is excluded. Required source facts are supply date, invoice issue date, customer Member State and USt-IdNr, qualifying-supply classification, and taxable base in cents. Use the invoice-issue month, but flag the report unavailable if the invoice was issued later than the statutory latest period (the calendar month after the supply). The preview aggregates taxable bases by customer USt-IdNr for one calendar month. An ordinary intra-community acquisition is an explicit nonreportable exclusion; §3a(2) services, §25b triangular deliveries, §6b movements, own-goods transfers, and other potentially reportable unsupported directions make the period unavailable rather than apparently empty. Quarterly election logic and ELSTER/BZSt submission are not implemented. This limited contract follows the current text of [§18a UStG](https://www.gesetze-im-internet.de/ustg_1980/__18a.html) as checked on 4 October 2026, especially paragraphs 1, 4, and 6–8.

6. **Separate a management GuV from a statutory-duty warning.** A management GuV is an optional accounting view, not a claim that §141 AO applies. Threshold amounts alone SHALL NOT assert bookkeeping duty or auto-enable a statutory-duty state. A duty warning is unavailable unless the profile has verified evidence of the qualifying business type, the correct calendar-year or fiscal-year threshold basis and measured amount, the Finanzamt finding/notice date, and the resulting effective date. For trade, §141(1) uses total turnover above €800,000 in a calendar year or trade profit above €80,000 in a fiscal year; for agriculture/forestry, profit above €80,000 in a calendar year. Under §141(2), the duty starts at the beginning of the Wirtschaftsjahr following the Finanzamt notice. The effective date SHALL come from verified notice/evidence and the profile's supported Wirtschaftsjahr boundary; January 1 SHALL NOT be assumed for a non-calendar Wirtschaftsjahr. A notice/evidence record is required; the app does not infer one. See [§141 AO](https://www.gesetze-im-internet.de/ao_1977/__141.html).

7. **Pin DATEV to a complete EXTF Buchungsstapel CSV.** The target is DATEV header version 700, category 21 (`Buchungsstapel`), format version 13. This exceeds DATEV's interface minimum of header 700 and Buchungsstapel version 12. No standalone Debitoren/Kreditoren master-data file is promised. The header follows the official 31-field sequence: fields 1–5 are `EXTF`, `700`, `21`, `Buchungsstapel`, `13`; field 6 is the generated timestamp; field 7 is blank; field 8 is `RE`; fields 9–10 are blank; fields 11–12 are configured Berater- and Mandantennummer; field 13 is the business-year start; field 14 is configured Sachkontenlänge; fields 15–16 are the selected month's inclusive dates; field 17 identifies the stack; field 18 is blank; fields 19–21 are `1`, `0`, `0`; field 22 is `EUR`; fields 23–26 are blank; field 27 is the configured supported chart code (`03` or `04`); and fields 28–31 follow the official v13 header definition. Each booking row follows the exact v13 field order (125 positions, unused fields empty). Core mapping is: field 1 positive amount with comma decimal; field 2 debit/credit indicator for field 7; field 7 account and field 8 counter-account from the accepted posting legs; field 9 configured tax key where required; field 10 source document date (`TTMM`, year from field 13); field 11 source document number; field 12 due date only when available; field 14 source description; and field 20 a DATEV-supported persisted document link only where the source has a valid supported link representation. A local file path is not a DATEV link. If an event with a required document has no supported link representation, export fails closed. Foreign-currency fields 3–6, tax/OSS fields 40–41 and 119–120, service-period fields 115–116, and correction field 118 are populated only from explicit supported source data; otherwise the affected export is unavailable. Partner account numbers must be explicit in field 7 or 8. Missing account, counter-account, required tax key, partner account, source date, or required document identity fails closed with source ID and field. No `1200`, `8400`, or other fallback is allowed. The official DATEV documentation does not define one universal text encoding for all transfers; the versioned fixture must pin the encoding/escaping accepted by the DATEV format validator and include umlaut/special-character cases. Use the [DATEV header](https://developer.datev.de/de/file-format/details/datev-format/format-description/header), [Buchungsstapel field specification](https://developer.datev.de/de/file-format/details/datev-format/format-description/booking-batch), and [EXTF interface requirements](https://developer.datev.de/de/product-detail/accounting-extf-files/2.0/documentation/interface-requirements-file) as the versioned sources. The fixture must assert header/version, 125-column rows, field mappings, decimal/date/escaping rules, and pass the DATEV format validator; header acceptance alone is insufficient. The export remains unavailable until its accepted posting source and all required mappings exist.

8. **Keep report previews and file artifacts distinct.** EÜR, EKS, GuV, UStVA, and ZM are on-screen previews only in this change. The sole new report file is the DATEV CSV, written to a user-selected safe destination and entered into history only after reopening and validating it. A preview or local file is never `Übermittelt`; that status needs an external receipt/confirmation. Existing GoBD export behavior remains governed by its existing contract.

9. **Preserve accessibility and dense-table usability.** Workspaces use the design-system controls, keyboard navigation, visible focus, localized loading/empty/error/unavailable states, and responsive layouts that do not clip report fields at narrow desktop widths.

## Risks / Trade-offs

- [The financial source or money rules remain unapproved] → Keep dependent totals and exports unavailable; do not fall back to current journal or invoice aggregations.
- [Annual totals may not cover a non-calendar tax period] → Do not infer a company fiscal calendar; add a reviewed period contract before supporting it.
- [The BMF changes EÜR forms by year] → Pin year-specific source and field-map fixture; reject unsupported years.
- [DATEV format version and fields change] → Pin version 13, validate the complete fixture, and require a reviewed version change before upgrading.
- [ZM has transaction classes not represented by this phase] → Report unavailable if the source indicates any potentially reportable unsupported transaction; never show a false empty report.
- [A threshold can be mistaken for a legal bookkeeping duty] → Keep the management GuV separate and require verified notice evidence for a §141 warning.

## Migration Plan

No database migration is required. First obtain independent approval for the balanced-posting/settlement and invoice-money source contracts. Then accept the year-specific EÜR mapping and ZM/§141 source fields before enabling those calculators. Wire only report services whose capability, period, and source prerequisites are satisfied. Build and validate the pinned DATEV v13 CSV fixture before enabling its export. Report previews never write journal entries; only DATEV uses the existing artifact lifecycle in this change.
