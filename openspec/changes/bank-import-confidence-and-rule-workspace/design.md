# Design: Bank Import Confidence and Rule Workspace

## Context

`/banking` currently builds `BankImportService` from the page and database executor. Review does not show the service's 40/30/30 score or a journal candidate. Rule matching exists in `auto_filter_regeln`, but users cannot manage rules. The page does not pass the service's mode argument, so imports always use its manual default. History and rejected-attempt persistence also perform database work in the widget. Existing retry only keeps failed rows in the current page state and cannot resume after history is reopened.

The change extends the existing import workflow. The archived `bank-import-workflow-integrity` contract remains authoritative for confirmed imports and deduplication. Maintained `bank-import` and `bank-import-recovery-surface` specs remain the capabilities being refined. New journal postings, payment creation, and settlement allocation remain out of scope and governed by `balanced-journal-postings-and-settlement-events`.

## Decisions

1. **Use one application-scope banking use case and typed repository boundary.** `/banking` resolves its workspace use case from `AppScope`/`AppServices`. The use case coordinates upload, score preview, rule management, profile mode, history queries, retry, and review actions through a typed `BankImportRepository`; the repository owns database access through the bank-import data source/service. SQL executors and row maps stay below the page. New history, rejected-attempt, retry, and review operations use this boundary as well as the existing import path. This is the minimum boundary needed to comply with `runtime-composition-and-database-lifecycle`; it does not add a second banking route or a second rules store.

2. **Preview scores without changing accounting data.** Reuse `computeScore` and load persisted journal candidates through the use-case boundary. A candidate is eligible only when it has an integer ID; invalid or unparsable amount/date values contribute no points under the existing scorer. Sort suggestions by score descending, then journal ID ascending for stable display. Before confirmation, Review shows the best score, confidence label, and candidate date, amount, and description. If multiple candidates share the top score, show all tied candidates in the suggestion state. A database/query error is an unavailable state, distinct from a successful query with no candidates; automatic linking is disabled for that import after a candidate-query error. The user may continue only after seeing the unavailable warning and explicitly confirming the import. Scores never create a posting or payment.

3. **Only auto-link one unambiguous existing journal entry.** Both persisted and per-import modes require the existing explicit Review confirmation. In automatic mode, after confirmation, link a transaction only when exactly one eligible journal entry has the highest score and that score is at least 90. A tied top score, lower score, or unavailable candidate query leaves `journal_id` null and the transaction in the applicable review state. Recheck candidates at persistence time; a query failure there stores the confirmed transaction without a link and returns a typed unavailable diagnostic. Manual mode never links a score suggestion automatically. Neither mode creates a journal entry or payment. Each staged import begins with the saved profile mode; a user-selected override applies only to that staged import and is discarded on completion, failure, cancellation, restart, or profile switch.

4. **Keep rules in the existing table and use its actual matcher.** Add a Banking Rules view over `auto_filter_regeln`. Validate a non-empty trimmed Verwendungszweck pattern, an existing category ID, and an integer priority before persistence. Matching is case-insensitive substring against Verwendungszweck only. Among active rules, the first match wins in priority-descending, rule-ID-ascending order. Equal-priority rules therefore have deterministic behavior. Create, edit, priority changes, enable/disable, and delete affect future imports only. The review projection shows the category supplied by the selected rule; existing rows are not rewritten.

5. **Persist the profile mode in ordered migration 9.** Store the setting as `unternehmen.bank_import_manuell INTEGER NOT NULL DEFAULT 1 CHECK (bank_import_manuell IN (0, 1))`; `1` means manual and `0` means automatic. Fresh schema creation includes this column and sets `user_version` to 9. The ordered 8-to-9 migration adds the same column with manual default to existing version-8 databases, preserving existing rows. There is no `ensureOpen`/post-migration add-column fallback for this field. Any DDL or version update failure rolls back the migration, keeps the previous version and company data intact, and surfaces the schema-migration failure. Profiles with no company row still resolve to manual mode. Read/write of this value is behind the repository and scoped to the active profile database.

6. **Make persisted row failures versioned and safely retryable.** Only row-level failures produced after a confirmed import are retryable. Write `fehler_details` as a JSON envelope with `schema: "openaccounting.bank-import-failures"`, `version: 1`, `kind: "rows"`, and a `rows` array. Each row contains its one-based import row and source row numbers; `datum` (ISO date or null), `betrag` (decimal string), `raw_datum`, `raw_betrag`, `partner`, `verwendungszweck`, `gegenkonto`, `kategorie_id`, `journal_id`, and stable non-sensitive diagnostic codes. The validated decoder rejects unknown versions, wrong types, invalid IDs/dates, and missing required source fields as non-retryable history data. Legacy JSON arrays, plain strings, and message-only objects remain visible as sanitized diagnostics but cannot resume because they do not contain a complete validated row. A parser/template/file rejection has `kind: "file_rejection"` and safe diagnostic codes only; it cannot be retried from history because the source file is not retained. The user must select the file again, creating a new import attempt.

   The version-1 payload has this exact structure: `{ "schema": "openaccounting.bank-import-failures", "version": 1, "kind": "rows", "rows": [...] }`. Every row has positive integer `row` and `source_row`; nullable ISO `datum`; string `raw_datum`, `betrag`, `raw_betrag`, `partner`, `verwendungszweck`; nullable string `gegenkonto`; nullable positive integer `kategorie_id` and `journal_id`; and `diagnostic_codes`, an array containing only `invalid_date`, `invalid_amount`, `missing_required_data`, `database_write_failed`, or `unknown_row_failure`. `betrag` is the normalized two-decimal amount when parseable and otherwise the original reviewed amount text; raw fields preserve uploaded text exactly. Unknown keys are ignored for forward compatibility only within version 1; required fields, known enum values, types, positive row numbers/IDs, and date syntax are validated. Any failure of validation, unknown version, or unknown kind makes the payload non-retryable. The file-rejection envelope has the same schema/version and `kind: "file_rejection"`, `diagnostic_codes`, and no rows.

   The retry command takes an existing import ID and its corrected persisted failed rows. It verifies that the row belongs to the active profile, that its status is `teilweise` or `fehlgeschlagen`, and that the versioned payload is valid. It inserts only those rows under that same ID; it never creates another `bank_imports` record. Each failure remains in the payload until successfully inserted. Successful row data is removed from the failure payload, and existing child rows and their transaction IDs are untouched. A repeated retry processes only the remaining failed rows. When no row failures remain, clear the retry payload and set ingestion status to `importiert`; otherwise use `teilweise` when at least one transaction is persisted and `fehlgeschlagen` when none is persisted. Recompute imported, duplicate, and failure counts from persisted child rows and remaining payload in the same transaction as retry writes. Derive unresolved-review count from `bank_transaktionen.status = 'neu'`. Do not log raw bank fields or place them in status/error text. Failed payloads remain in the active profile database and its existing backup lifecycle; profile deletion removes them with that database. No separate retention store is introduced.

7. **Define manual review as a persisted state transition, not a category-null heuristic.** Reuse the existing `bank_transaktionen.status` text column with exactly three values: `neu` means awaiting explicit post-import review; `geprueft` means a user reviewed/classified it without linking a journal entry; `gebucht` means linked to an existing journal entry. No new column is needed. A user-selected category during import is `geprueft` unless linked; a rule-assigned category without an explicit user decision is still `neu`; an unlinked row with no category is `neu`; a journal-linked row is `gebucht`. Manual review selects only `status = 'neu'`. The user may assign/correct a category and confirm review (transitioning to `geprueft`) or associate an existing journal entry (transitioning to `gebucht`). Review cannot mark a row complete while it has neither a category nor journal link. Reopening the queue queries status, so already-reviewed rows disappear. Derive the history review count from `status = 'neu'`; the legacy `anzahl_manuelle_pruefung` scalar is not authoritative. History status SHALL retain existing persisted values: `importiert` means ingestion completed, `teilweise` means some rows persist and retryable failures remain, and `fehlgeschlagen` means no transaction persisted or a whole-file rejection occurred. A completed history attempt remains immutable, while its unresolved child transactions remain editable through the separate review action. Review edits never alter the import attempt's file metadata, status, or retryable-row payload.

8. **Make history search and pagination a typed route query.** `/banking` history state is `view=history`, `q=<query>`, `page=<1-based page>`, and optional `importId=<selected row>`. Search case-insensitively matches only filename, template type, and history status; it does not search or expose raw bank transaction payloads. Apply filtering before pagination. Sort newest timestamp first and import ID descending for timestamp ties. Use 50 rows per page and return total count plus `hasMore`. Opening detail or retry and returning to history preserves the complete query; an out-of-range page after deletion/filtering is clamped to the last valid page. The selection/detail state uses the canonical route query so it survives restoration and can be shared as a deep link.

9. **Reuse components that exist and stay inside `DESIGN.md`.** The repository implements `AppPage`, `AppPageHeader`, and `AppStatusChip`; it does not yet implement the documented `AppDataTable`, `FilterBar`, or `DetailInspector`. Use the available components and Flutter's existing table, form, focus, and layout widgets. Do not claim or add the missing shared primitives as part of this feature. Keep any wide table in a bounded scroll region. Localize labels, validation, errors, empty/loading/unavailable states, and accessible descriptions through generated resources. Provide logical focus order, visible focus, keyboard actions for all rule/history/review controls, and focus restoration when inspectors close. Verify German text expansion and text scaling at the documented compact widths; status and confidence always have textual or semantic meaning in addition to color.

10. **Correct the complete bank-import guide as part of implementation.** Update `docs/04-bank-import.md` so it no longer makes claims that contradict the maintained specs or Dart source:
    - Replace the “10+ templates” claim with only the implemented seven predefined CSV templates and describe custom templates only where implemented.
    - Describe Step 3 as storing confirmed rows in `bank_transaktionen`; explain that automatic mode may link one unambiguous existing journal entry, but does not create a journal entry or payment.
    - Remove CAMT.052 support claims; document the implemented CSV and CAMT.053 input and only parser behavior the Dart source supports.
    - Replace regex/partner/amount/combinations with `auto_filter_regeln` fields, case-insensitive Verwendungszweck substring matching, first active match, descending priority and ascending ID.
    - Replace category-rule/reconciliation score factors with the maintained 40/30/30 amount/date/partner contract and confidence labels.
    - Correct the duplicate hash input to date, normalized amount, partner, and Verwendungszweck; do not claim `partner_iban` is part of the hash.
    - Replace the illustrative storage schema with the actual `bank_transaktionen` fields, including the nullable journal link and current status semantics; remove unsupported index/field claims if they are not present in the source schema.
    - Replace Python, `chardet`, ElementTree, `hashlib`, JSON-template-seed, and WAL-concurrency implementation notes with verified Dart behavior; omit implementation details that cannot be verified.
    - Document ordered migration 9, manual default, per-profile scope, one-import reset, retry eligibility, review predicate, and history pagination/search.

## Failure and recovery boundaries

- A malformed or legacy failure payload is shown as a safe non-retryable diagnostic; it is never guessed into a transaction.
- A retry validates ownership and status before writing and is atomic with history count/status updates. A database failure leaves the prior import row, successful child rows, retry payload, and schema version usable.
- Candidate-query failure suppresses automatic association without fabricating a no-match score.
- Rule/category/journal-link writes report unavailable/failure states; the page does not substitute an empty rules list or empty history.
- Raw failed-row values remain only in validated persistence and the user's reviewed row display, not in diagnostic text, status, or logs.
