## Findings

### 🔴 Critical (blocking)

1. **History retry cannot reconstruct or resume the failed rows under their original import ID.** The design claims `fehler_details` already contains retryable row payloads and requires reuse of the original `bank_imports.id` (`design.md:33`; `specs/bank-import-recovery-surface/spec.md:5-10,30-33`). But `BankImportService.importTransactions` has no existing-ID/retry argument and unconditionally creates a new history row before inserting child transactions (`lib/features/bank_import/bank_import_service.dart:217-235`); `_finalizeHistory` then finalizes only that new ID (`:493-531`). The existing retry is only page-local state (`lib/features/bank_import/bank_import_page.dart:544-573`), so reopening history or restarting the app loses the editable rows. Historical failure data also is not a uniform, round-trippable format: row failures serialize a subset of fields with no decoder (`lib/features/bank_import/bank_import_entity.dart:120-132`), parser rejections can store message-only JSON or a plain string (`lib/features/bank_import/bank_import_service.dart:506-515`; `lib/features/bank_import/bank_import_page.dart:605-620`), and `_diagnosticText` only returns the raw text (`lib/features/bank_import/bank_import_page.dart:1564,1666`). The serialized row omits `gegenkonto`, selected category, and selected journal ID. Define a versioned, validated retry payload and legacy/message-only handling; persist every field needed to reproduce a failed reviewed row; distinguish row-retryable failures from rejected whole-file attempts; and define a service operation that validates an existing import ID, processes only its persisted failed rows, and merges counts/status/remaining failures without changing successful rows or their IDs. Add assertions for retry after reopening, legacy/malformed payloads, repeated retry, and unchanged `import_id`/transaction IDs. Existing tests instead expect two history records after retry (`test/features/bank_import/retry_dedup_test.dart:72-78`) and do not assert original-ID recovery.

2. **The manual-review set and its completion state are undefined, and the history contract contradicts itself.** The recovery delta says completed imports are read-only, while also making manual review available for imports with a positive stored count and allowing category or journal-link updates (`specs/bank-import-recovery-surface/spec.md:5-13,25-43`). The spec never defines whether “completed” means ingestion complete or all review complete. Nor does it define which rows are unresolved or how a review action resolves them. Today the stored count is based on whether a rule auto-assigned a category (`lib/features/bank_import/bank_import_service.dart:276-280,323-327`), while persisted transaction status is only `gebucht` when linked and `neu` otherwise (`:302-320`); the table has no separate review state (`lib/core/db/database.dart:653-665`). A count cannot identify the rows to display, and category correction alone versus journal association has no specified effect on that set. Specify a row-level unresolved predicate and state transition, make the meaning of “completed/read-only” consistent with permitted review edits, and define how the count is updated or derived after edits and retries. Add cases for rule-categorized-but-unlinked, manually categorized, linked, and already-reviewed rows across completed and partial imports.

3. **Automatic linking can choose an arbitrary journal entry when top candidates tie.** The delta links the best candidate automatically at 90% or more (`specs/bank-import/spec.md:47-83`), while the design leaves candidate loading/ranking to the existing scorer (`design.md:30,39`). The existing import query is `SELECT * FROM journal` with no order (`lib/features/bank_import/bank_import_service.dart:237-242`), and ranking replaces the winner only for a strictly greater score (`:282-299`); equal top scores therefore select whichever row SQLite happens to return first. Two entries can both score 100 under the specified 40/30/30 contract, yet `journal_id` and the “Gebucht”/export behavior will silently use one. Specify candidate eligibility and tie behavior. A safe contract is to auto-link only a unique high-scoring candidate and leave tied candidates unlinked for manual selection; add a duplicate-100%-candidate scenario. Also distinguish a failed candidate query from a genuine no-match: current code catches query errors and turns them into an empty candidate list (`:237-242`), which the new UI could mislabel as `0%`/“Keine”.

4. **The profile-mode column plan conflicts with the maintained ordered-migration contract.** `unternehmen.bank_import_manuell` is new (`design.md:32,46-48`), but the design only says “existing additive migration path” and does not say how the stored boolean/mode is encoded, how a fresh schema defines it, or which migration upgrades existing profiles. The current schema has no column (`lib/core/db/database.dart:363-405`); the migration runner is at version 8 (`lib/core/db/migrations.dart:14`) and its ordered migrations run before separate add-if-missing schema changes in `ensureOpen` (`lib/core/db/database.dart:142-168,195-215`). The active spec requires every production column to be introduced by an ordered migration and prohibits runtime schema creation as a workflow side effect (`openspec/specs/schema-evolution-safety/spec.md:8-24`). Specify the ordered migration/version bump, fresh-schema default, existing-profile manual default, and exact stored/read values; do not rely on the post-migration `ensureOpen` fallback. Cover fresh and version-8 profile databases and migration rollback/failure in the test scenarios.

### 🟡 Moderate

1. **The route/data plan omits the maintained application-scope boundary.** The runtime composition spec requires production pages to resolve use cases from application scope and forbids query executors/raw SQL in widgets (`openspec/specs/runtime-composition-and-database-lifecycle/spec.md:26-42`). The proposal acknowledges the existing page's direct database access and proposes extending `BankImportService`, but history reads and rejected-import writes currently remain in `BankImportPage` (`design.md:3,31,33`; `lib/features/bank_import/bank_import_page.dart:24-27,209-245,605-632`). State the owning use case/repository/data-source boundary for new rules, profile mode, history detail, retries, and review updates; the updated `/banking` route should consume that boundary rather than expand widget-level database access.

2. **The design relies on components that are described but not implemented.** Decision 6 says to reuse `AppDataTable`, `FilterBar`, and `DetailInspector` as existing components (`design.md:35`). `DESIGN.md:1710-1784` describes these primitives, but the repository only has implementations for `AppPage`, `AppPageHeader`, and `AppStatusChip`; the current Banking page uses Flutter `DataTable` (`lib/features/bank_import/bank_import_page.dart:1137-1153`). Update the design to use the available components, or explicitly scope only the minimum shared component work this feature needs. No new dependency appears necessary; Flutter, Drift, and existing localization generation cover the described UI and storage work.

3. **The promised documentation alignment leaves material false claims in place.** `design.md:34` says the documentation will reflect the actual Dart workflow, but the listed replacements cover only score factors, rule fields/order, mode, and history. `docs/04-bank-import.md` still says the workflow creates journal entries (`:14-17,37-40,254-277`), describes Python parsing and `chardet` (`:142,283-288`), and documents duplicate hashing with `partner_iban` (`:202-206`) whereas current Dart hashes date, amount, partner, and purpose (`lib/features/bank_import/bank_import_service.dart:45-53`). Specify correcting or removing all contradicted workflow, posting, schema, hash, and implementation-language claims in the sections this change will leave behind.

4. **History pagination/search is not yet mechanically specified for the existing 100-row query.** The delta requires search, pagination, and returning to the same query/page (`specs/bank-import-recovery-surface/spec.md:5-10,45-48`), but it does not define searchable fields, ordering, page size, total/has-more behavior, or whether filtering happens before pagination. Current history reads only the newest 100 rows (`lib/features/bank_import/bank_import_page.dart:213-235`) and has no search or pagination controls. Define the query contract so older history remains reachable and add a fixture exceeding one page with active filtering and detail-return assertions, consistent with `typed-route-workspaces` (`openspec/specs/typed-route-workspaces/spec.md:46-58`).

5. **The retryable-payload retention question is left open despite persisting raw financial data.** Failed-row JSON contains amount, partner, purpose, and raw source values (`lib/features/bank_import/bank_import_entity.dart:120-132`) and is stored in the profile database/backups. `design.md:52-53` explicitly leaves retention/erasure undecided. Define when repaired payloads are cleared and how still-failed payloads follow the profile’s deletion/backup lifecycle; keep raw bank values out of error/status text and logs. This matters particularly for message-only legacy history, which currently may expose raw JSON as a history tooltip (`lib/features/bank_import/bank_import_page.dart:1164-1188,1563-1565`).

6. **The UI acceptance scenarios do not verify several claimed accessibility and localization behaviors.** The spec claims keyboard controls, focus order, visible focus, generated strings, and responsive layouts (`specs/bank-import/spec.md:85-104`), but the two scenarios only check rendered views and reachability. Add observable keyboard actions for rule create/edit/priority/toggle/delete, opening/closing details, and retry/review; assert semantic labels and focus restoration, plus German text expansion and text scaling at the stated widths. `DESIGN.md:1110-1144,1187-1203,1450-1469,1983-2021` requires those behaviors and locale-aware formatting.

### 📌 Suggestions

- Keep rule semantics exactly aligned with the existing matcher: case-insensitive substring on `Verwendungszweck`, first active match wins, descending `prioritaet`, then ascending ID (`bank_import_service.dart:56-80`; delta `bank-import/spec.md:19-45`). Include an explicit equal-priority example and validate non-empty pattern, existing category, and integer priority through parameterized CRUD operations.
- The score/mode tests should assert both profile isolation and one-import override reset; the current page never passes a mode (`bank_import_page.dart:473-479`) while the service defaults to manual (`bank_import_service.dart:217-224`). Also make explicit that both modes still require the import confirmation and that automatic mode only changes post-confirmation linking, never creates postings or payments.
