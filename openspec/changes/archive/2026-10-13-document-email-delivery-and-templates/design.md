## Context

The feature map describes per-document message templates and sending business documents through SMTP, including reminders and related files. Production has no mail transport: `MahnungenRepository.sendMail()` only changes reminder status, and `UnternehmenRepository.testSmtp()` opens and closes a socket without SMTP greeting, TLS upgrade, or authentication. The current repository has a file-backed `.smtp_secret`, legacy `smtp_ssl` and certificate-bypass settings, and a database password column that startup code clears. The settings and dunning proposals are active separately, so this change must define a shared transport contract without taking ownership of their navigation or reminder eligibility.

## Goals / Non-Goals

**Goals:**

- Send user-confirmed messages from the production `/invoices/:id` detail route for eligible finalized `Rechnung`, `Angebot`, `Auftrag`, and `Proforma` documents through authenticated SMTP with required TLS.
- Let users edit per-type plain-text subject/body templates for those first-release types and safely preview one-send overrides.
- Attach only the generated document and explicitly selected, related existing artifacts.
- Record the exact SMTP outcome without claiming downstream delivery.
- Keep mail submission and credential access behind registered services and secure platform storage.

**Non-Goals:**

- Automatic sending, scheduled retry, external mail-client handoff, read/delivery tracking, or arbitrary filesystem attachments.
- Sending `Lieferschein` or `Mahnung` in the first release. `Lieferschein` awaits a persisted artifact provider. `Mahnung` awaits its production detail route and accepted dunning/artifact/send contracts.
- Creating invoice, reminder, account-statement, or other document artifacts; each owning capability must provide an eligible artifact and recipient.
- Deciding whether a reminder may be sent; dunning owns balance, stage, and duplicate-reminder rules.
- Building a bespoke SMTP, TLS, or MIME implementation.

## Decisions

1. **Use one shared application transport boundary with a bounded first-release matrix.** The first release supports `Rechnung`, `Angebot`, `Auftrag`, and `Proforma` through the existing `/invoices/:id` route (`InvoiceDocumentPage`), backed by `RechnungenUsecases.findById` and a new typed `DocumentDeliveryContext` assembled from the route's document ID, its `RechnungItem`, and the linked customer record through registered application/repository services. A type is eligible only when finalized and its linked, generated PDF artifact is present. The recipient defaults to the linked customer's primary email, resolved by that context provider; the user may edit one recipient for the attempt. Attach the document's stored `originalPdfPath` artifact and explicitly selected, existing artifact IDs linked to that same document. These four types share the route and artifact provider but keep separate templates keyed by their typed document type. `Lieferschein` is deferred because its creation path does not currently guarantee a persisted generated PDF artifact. `Mahnung` is deferred because it has no production detail route and its accepted dunning and artifact contracts are still gated. No deferred type may expose a send action. Document features construct typed requests; a registered delivery service validates them and calls a maintained SMTP/MIME library through one transport adapter. UI widgets do not read the database or open sockets. Before implementation, select a maintained dependency that supports implicit TLS, required STARTTLS, AUTH, MIME attachments, and every supported desktop target.

2. **Require verified TLS before SMTP authentication.** The configuration stores either `implicit_tls` or `starttls_required`, not an ambiguous SSL boolean. Both modes require TLS 1.2+, valid certificate chain and hostname, then SMTP AUTH. For required STARTTLS, send EHLO again after TLS negotiation and choose AUTH only from the post-TLS capabilities. A configured SHA-256 certificate pin can further restrict a valid certificate but cannot bypass normal validation. Port number does not silently select a security mode. Port 25/plaintext is not supported, and failed STARTTLS never falls back. This follows the SMTP STARTTLS and AUTH mechanisms in [RFC 3207](https://www.rfc-editor.org/rfc/rfc3207.html) and [RFC 4954](https://www.rfc-editor.org/rfc/rfc4954.html); [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html) recommends TLS 1.2 or later and prefers implicit TLS for message submission.

3. **Use the operating system credential vault and migrate before destructive cleanup.** Give every profile an immutable ID stored in profile metadata; use that ID, not profile name or path, as the vault key so profile rename preserves credentials. On startup, read the profile ID and migrate any legacy database password or `.smtp_secret` value before `AppDatabase.ensureOpen()` or `UnternehmenRepository._ensureSchema()` can clear the database password. Write to the vault, read back and verify the value, then remove the old copy. If the vault is unavailable, disable SMTP and preserve the existing legacy source for retry; never create a new plaintext copy or clear the only recoverable value. Existing passwords already cleared by an earlier app version cannot be recovered and must be re-entered. Do not log secrets or include them in send history.

4. **Test the full connection without sending.** The test operation performs greeting and EHLO, the configured TLS negotiation, a second EHLO after STARTTLS, and authentication using the post-TLS advertised capabilities, then closes. It does not issue MAIL, RCPT, or DATA. Its result lists completed operations rather than saying only “connected.” A timeout or protocol/auth failure is explicit and never triggers a plaintext retry.

5. **Render only a small, typed placeholder allowlist.** Seed and edit a profile-local plain-text subject/body pair by supported document type. Initially support `{dokumentnummer}`, `{betrag}`, `{faelligkeit}`, and `{firma}` when the typed context contains those values. `{betrag}` uses the persisted canonical total and shared locale-aware money formatter. Unknown or unavailable tokens block send preparation; do not silently insert an empty string or infer a due date. Expand in the application use case. Parse sender and recipient as exactly one mailbox and reject CR/LF in either address or subject before constructing MIME headers; body newlines remain plain text. Per-send edits are discarded unless the user explicitly saves the template.

6. **Review the exact message before network access.** Default one recipient from the linked customer's primary email and allow the user to edit one address for this attempt. Show sender, recipient, expanded subject/body, document type/number, and every attachment filename in a localized preview. Only then may an explicit confirmation submit. Attachments are artifact references, not paths: the selected generated artifact and user-selected existing artifacts linked to that document are allowed. The registered artifact resolver verifies both document ownership and canonical resolved-path containment under the active profile root before reading bytes; reject symlink targets outside the root. Callers cannot nominate arbitrary disk paths.

7. **Record three transport outcomes and make owner updates atomic and recoverable.** Persist a minimal profile-local attempt row as `submitting` before network transmission, including a stable source-document ID and, for any future accepted dunning integration, a stable `mahnung_id` and attempt idempotency key. After SMTP returns its successful final response, use one local database transaction to persist the attempt as `accepted`, set invoice `ausgegeben_am` if still null, and apply the owning dunning service's idempotent reminder-status/invoice-stage projection when the attempt is for a reminder. Do not mark the attempt `accepted` unless the owner projection commits in that same transaction. Explicit final rejection is `rejected`; a failure proven before message submission is `rejected`; loss after DATA or failure before the final transaction commits is `unknown`. Recovery converts abandoned `submitting` attempts to `unknown`, never resubmits them, and keeps the stable reminder reference attached. An `unknown` reminder attempt blocks automatic creation or sending of another reminder for the same source event; retrying that same reminder requires explicit duplicate-risk confirmation. This change's first release does not expose Mahnung sending; the transaction contract is a prerequisite for the later dunning integration. Do not persist full bodies, attachment bytes, or credentials. The UI says “accepted by SMTP server,” not “delivered.” Duplicate UI calls share the in-progress attempt and do not issue a second DATA command.

8. **Make this the single SMTP contract and order dependent changes.** This capability is the source of truth for SMTP fields, credential storage, test semantics, transport, and send history. The Settings workspace owns navigation and presents controls backed by this registered capability. Before implementation, update the active `settings-setup-workspace-completion` change to remove its competing file-backed `SmtpSecretStore` design and depend on this credential adapter. Update the active `dunning-workflow-integrity` change to consume this registered transport and the atomic owner-update contract before it adds a send surface or changes reminder status after acceptance. Both cross-change references and the implementation order must be reconciled and accepted before either Settings SMTP controls or dunning sending is implemented. Document-detail surfaces own preview and send actions according to `DESIGN.md`.

9. **Correct the feature guides.** Feature 08 must remove plaintext port 25 and certificate-ignore examples, distinguish implicit TLS from required STARTTLS, and state that test connection authenticates but sends nothing. Feature 01 and Feature 05 must distinguish user-confirmed SMTP acceptance from actual delivery and explain that related attachments must already exist as app artifacts.

## Risks / Trade-offs

- [An OS credential vault is unavailable or locked, especially on Linux] → Disable SMTP clearly and require the user to unlock/configure the OS vault; do not fall back to a plaintext secret file.
- [A connection can drop after the server accepted DATA] → Record `unknown`, warn about possible duplicates, and require explicit user confirmation before retry.
- [A document type lacks a generated artifact or typed placeholder value] → Keep its send action unavailable and identify the missing document field/artifact; the mail change does not fabricate it.
- [Existing file-backed secrets cannot be atomically moved with the database migration] → Use idempotent vault-first migration and only then remove the old copy; if vault write fails, disable SMTP and surface recovery rather than losing the credential silently.
- [SMTP acceptance is mistaken for delivery] → Use transport-specific UI wording and do not expose delivered/read states without an independent receipt source.

## Migration Plan

1. Select and verify a maintained SMTP/MIME and OS-vault adapter for Windows, macOS, and Linux. Block implementation if any supported target cannot enforce the contract.
2. Add the explicit transport-mode setting. Map legacy `smtp_ssl = true` to implicit TLS and `false` to required STARTTLS; never map it to plaintext. Drop the certificate-ignore option and retain fingerprints only as an additional constraint.
3. Before opening the database, ensure profile metadata has an immutable profile ID, then migrate recoverable DB/file secrets into the vault under that ID. Verify a vault read before clearing either old copy. If the vault is unavailable, preserve the only legacy source for migration recovery, keep SMTP disabled, and ask the user to retry or re-enter credentials; never clear the source before verification.
4. Add the document-attempt and template persistence migrations. Existing finalized documents and their accounting data remain unchanged.
5. Release the Settings controls and user-confirmed send surfaces after the selected adapters pass platform checks. On rollback, disable SMTP and require credentials to be re-entered into the vault; never recreate the old plaintext storage path.
6. Update docs 01, 05, and 08 to match the shipped behavior and validation evidence.
